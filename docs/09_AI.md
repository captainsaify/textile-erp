# 09 — AI Natural Language Queries

## 1. Why this is not "send the question to an LLM with DB access"

The tempting naive design is: forward the user's WhatsApp question and
a DB schema description to an LLM, let it write SQL, run the SQL,
return the answer. This is explicitly rejected for this system:

- **SQL injection / destructive-query risk**: an LLM-generated query
  run directly against production is one prompt-injection or
  hallucination away from `UPDATE`/`DELETE` or a runaway join. This is
  an accounting system — the cost of a wrong or malicious write is
  unacceptable.
- **Non-determinism**: "how many TRP are left" must return the exact
  number `stock TRP` would show — an LLM re-deriving the answer via a
  freshly generated query each time risks subtly different (or
  outright wrong) aggregation logic (e.g., forgetting `deleted_at IS
  NULL`, or getting the weighted-average join wrong) with no way to
  guarantee consistency.
- **Auditability**: every other command in this system is fully
  deterministic and testable end-to-end; an open-ended text-to-SQL
  layer would be the one part of the system whose behavior isn't
  pinned down by a spec, which conflicts directly with
  [`CLAUDE.md`](../CLAUDE.md#non-negotiable-philosophy)'s "no mocked
  business logic" / "not a CRUD app" stance applied to correctness,
  not just to write paths.

**What is built instead**: intent classification + slot extraction
(via a small, constrained LLM call) that maps a natural-language
question to one of a **fixed, enumerated set of pre-built,
parameterized queries** — the same query methods the WhatsApp commands
and dashboard already use (`InventoryValuationService`,
`LedgerService`, `ProfitService`, etc.). The LLM's only job is
figuring out *which* known question is being asked and *which*
parameters (product, customer, date range) it needs — never generating
SQL itself.

## 2. Architecture

```mermaid
flowchart LR
    U[WhatsApp: natural language question] --> Router{Matches a known\nWhatsApp command\nsyntax directly?}
    Router -- yes --> Cmd[Handled as that command\n08_WhatsApp.md]
    Router -- no --> Intent[Intent classifier\n+ slot extraction]
    Intent --> Match{Confident match to\na known AI intent?}
    Match -- yes, high confidence --> Exec[Call the corresponding\nservice method\n(same ones commands use)]
    Match -- yes, low confidence --> Confirm["Did you mean: <interpretation>?\nreply yes/no"]
    Match -- no --> Fallback["I'm not sure how to answer that.\nTry 'help' for supported commands\nor rephrase."]
    Exec --> Format[Format result as\nWhatsApp-friendly text]
```

- **Intent classifier**: a bounded prompt to an LLM (see
  [claude-api skill](../CLAUDE.md) reference for current model
  choice — a small/fast model is sufficient since the task is
  classification over a fixed intent list, not open-ended generation)
  that receives the user's text plus the enumerated intent catalogue
  (§3) with each intent's required slots, and returns **structured
  JSON** (`{intent: "customer_outstanding_max", slots: {}}`) —
  never free text, validated against a strict Pydantic schema before
  use, and if the response doesn't parse as valid structured output it
  is treated as "no confident match," never retried with a looser
  parser that might accept malformed output.
- **Slot resolution**: extracted entity names (customer/supplier/
  product references) are resolved through the **same fuzzy-matching
  services** used by WhatsApp commands
  ([07_OCR.md §9](07_OCR.md#9-fuzzy-matching-against-the-product-catalog),
  [04_Purchases.md §7](04_Purchases.md#7-validation-rules-exhaustive)) —
  not re-implemented for AI queries, so "TRP" resolves identically
  whether typed in a `stock` command or asked about in a question.
- **Execution**: the matched intent maps 1:1 to an existing, tested
  service method. The AI layer contributes *zero* new business logic
  or aggregation code — it is purely a routing layer in front of
  functionality that already exists and is independently correct.

## 3. Supported intent catalogue (v1)

| Intent | Example question | Slots | Backing service method |
|---|---|---|---|
| `stock_remaining` | "How many TRP are left?" | `product` | `InventoryService.get_stock(product)` |
| `todays_profit` | "Show today's profit" | `date_range` (defaults today) | `ProfitService.calculate(range)` |
| `customer_outstanding_max` | "Who owes us the most money?" / "Who owes us money?" | — | `LedgerService.top_receivables(limit)` |
| `purchases_in_period` | "What did we buy last month?" | `date_range`, optional `supplier` | `PurchaseService.list(range, supplier)` |
| `best_supplier` | "Best supplier?" | optional `metric` (cheapest / most reliable / highest volume) | `SupplierAnalyticsService.rank(metric)` |
| `highest_margin_item` | "Highest margin item?" | optional `date_range` | `ProfitService.margin_by_product(range)` |
| `cheapest_supplier_for_product` | "Which supplier gives the cheapest jogging pants?" | `product` | `SupplierAnalyticsService.cheapest_for(product)` |
| `inventory_above_value` | "Show inventory worth more than ₹50,000" | `amount_threshold` | `InventoryValuationService.products_above(threshold)` |
| `supplier_outstanding` | "How much do we owe Shree Textiles?" | `supplier` | `LedgerService.payable(supplier)` |
| `low_stock_items` | "What's running low?" | — | `InventoryService.low_stock_list()` |
| `sales_in_period` | "How much did we sell this week?" | `date_range` | `SalesService.total(range)` |
| `product_sales_history` | "How much TRP have we sold this month?" | `product`, `date_range` | `SalesService.by_product(product, range)` |

Every intent's slot schema, backing method signature, and the exact
WhatsApp phrasing tested against it are defined together in
`backend/ocr/../services/ai_intents.py` (a single source-of-truth
registry — the classifier prompt is generated *from* this registry at
startup, not maintained as separate hand-written prompt text that
could drift from the actual intent list, mirroring the
[command-registry pattern](17_CodingStandards.md#command-registry-pattern)
used for WhatsApp commands themselves).

## 4. Confidence handling and fallback

- **High confidence** (classifier returns intent + all required slots
  resolved unambiguously): answered directly.
- **Medium confidence** (intent clear, but a slot is ambiguous — e.g.
  "best supplier" with no metric specified defaults to
  `most_reliable` defined as fewest duplicate/mismatch flags and most
  on-time-priced purchases, but the response states which
  interpretation was used: "Based on price consistency and order
  history, Shree Textiles. (Ask 'cheapest supplier' or 'most
  reliable supplier' to be specific.)").
- **Low confidence / no match**: never guesses — responds with the
  fallback shown in the diagram, plus (for questions that are close but
  not quite matching a known phrasing) a suggestion of the nearest
  known command, e.g., "Did you mean 'stock TRP'?"
- **Never silently answers wrong**: because every answer is backed by
  a deterministic service call rather than free-form LLM generation,
  the failure mode is always "doesn't understand the question," never
  "confidently states a wrong number" — this is the core safety
  property this design is built to guarantee, and it's why intent
  classification (bounded, verifiable) was chosen over open-ended
  RAG/text-to-SQL for a system where wrong numbers are a real cost.

## 6. Permissions

AI queries respect the same RBAC as the equivalent underlying command
— a question that resolves to `profit`-equivalent data is owner-only
even if asked conversationally by staff; the AI router checks the
resolved intent's declared minimum role **before** executing, exactly
like the command dispatcher does (§4 in
[08_WhatsApp.md](08_WhatsApp.md#4-permissions-model-referenced-by-every-command-below)),
reusing the identical permission-check code path rather than a
parallel one.

## 7. Failure scenarios

| Scenario | Behavior |
|---|---|
| LLM API unavailable | Falls back to a simple keyword-based matcher against the intent registry's example phrasings (`rapidfuzz` similarity against known example questions) for basic coverage; if that also fails to match, the standard "I'm not sure" fallback fires — the system never blocks a user's whole session on an external AI API being down. |
| Question mixes two intents ("who owes us the most and what's our profit today") | Classifier is prompted/allowed to return multiple intents per message; each is executed and answered in sequence in one reply. |
| Slot resolves to multiple equally-plausible entities (ambiguous customer name) | Same disambiguation pattern as regular commands (§ [05_Sales.md §10](05_Sales.md#10-failure-scenarios)) — numbered options, no silent pick. |
| User asks something structurally answerable but outside the v1 intent catalogue (e.g., "what's our year-over-year growth") | Explicit "not supported yet" rather than a strained partial match — logged (question text + timestamp, no other context) to a `ai_unmatched_queries` table so real, recurring unmet needs can inform which intents to add next, a lightweight feedback loop without speculative catalogue bloat. |
| Sensitive intent asked by non-owner via natural language as a way to route around the direct command's permission check | Blocked identically per §6 — natural-language phrasing is not a permission bypass. |

## 8. Performance & cost

- Each AI query costs one small LLM call for classification (cheap,
  low-latency model — see [claude-api](../CLAUDE.md) skill for current
  guidance on model selection for lightweight classification tasks)
  plus one deterministic DB query — no LLM call is made to *generate*
  the answer text for numeric results (the response is templated from
  the structured service-method result), keeping both latency and cost
  predictable and bounded regardless of query complexity.
- Classifier responses for identical/near-identical question text are
  cached briefly in Redis (5 min TTL) since the partners sometimes
  repeat a question ("what's today's profit" asked twice in an hour) —
  cache key includes the resolved intent+slots, not raw text, so
  paraphrases still hit the same cache entry once classified once.
